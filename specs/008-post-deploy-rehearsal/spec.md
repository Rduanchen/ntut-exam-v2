# Feature Specification: Post-Deployment Rehearsal (部署後測試)

**Feature Branch**: `[008-post-deploy-rehearsal]`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "當系統部署完成後，有一個選項是讓使用者執行『部署後測試』。助教按下按鈕後，後端會自動模擬上傳 config 檔案，並以 call api 的方式模擬學生取得測試資料、模擬學生送出檔案並執行，最後模擬助教端手動評測；測試完之後把系統清掉。目的是在考試開始之前確認一切正常，這是考試開始前的最後一套防線。"

> **相關文件**：`../006-judger-deploy-test/spec.md` 驗證的是**評測引擎本身**（語言、判定、併發）。本功能驗證的是**整條考試流程**（上傳考卷 → 學生取卷 → 學生提交 → 助教評測）。兩者互補，不重疊：前者回答「這台機器跑不跑得動程式」，後者回答「這套系統走不走得完一場考試」。`../../EXAM-LIFECYCLE.md` 定義本功能必須走完的階段順序與權限矩陣。

## Context

部署到新考場之後，硬體、網路、設定檔、資料庫、評測引擎全部是新的組合。目前可用的驗證手段只能各自證明「某一段是好的」：健康檢查證明評測引擎活著，部署測試證明程式跑得起來，但**沒有任何一項證明這四段接得起來**。真正會在考試當天爆炸的，往往是接縫——考卷切分後學生取不到、加密通道對不上、提交寫不進資料庫、助教按下評測沒有反應。

本功能把「走完一場最小的考試」變成一個助教可以按下去的動作。它不是模擬器，也不是單元測試：它使用**真實的部署、真實的 API、真實的資料庫與真實的評測引擎**，只是把學生與助教的動作換成後端自己發出的請求。走得完，代表這台機器今天可以辦考試；走不完，代表在學生進場前就已經知道問題出在哪一段。

跑完之後系統必須回到乾淨狀態，因為它的每一步都在真實系統上留下痕跡。**一次沒有清乾淨的演練，會讓正式考試帶著演練的殘留資料開始**——那比不做演練更危險。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一鍵走完一場最小的考試 (Priority: P1)

助教在部署完成、正式上傳考卷之前，於管理端按下「部署後測試」。系統自動依序完成：載入一份演練用考卷並初始化、推進階段、以學生身分取得考卷資料、以學生身分提交程式碼、以助教身分觸發評測並取得分數。助教全程留在同一個畫面上，看得到現在走到哪一段、每一段過了沒有。

**Why this priority**: 這是本功能存在的理由。任何一段拆開來單獨驗證都已經做得到；有價值的是「一次走完、而且是同一條路走完」。

**Independent Test**: 在一台剛部署好、尚未初始化的機器上按下部署後測試，確認它在無人介入的情況下走完全部階段，並在同一個畫面回報逐段結果與整體結論。

**Acceptance Scenarios**:

1. **Given** 一台剛部署完成、尚未初始化的系統, **When** 助教啟動部署後測試, **Then** 演練開始執行，且助教在同一個畫面看到目前進行到哪一段。
2. **Given** 演練正在執行, **When** 助教觀看進度, **Then** 每一段（考卷載入、階段推進、學生取卷、學生提交、助教評測、清除）各自顯示未開始／進行中／通過／失敗。
3. **Given** 演練全部通過, **When** 演練結束, **Then** 畫面顯示整體結論為「通過」，並列出每一段的耗時與關鍵觀察值。
4. **Given** 任一段失敗, **When** 演練結束, **Then** 整體結論為「失敗」，並明確指出是哪一段、失敗原因，以及該段之後的步驟未被執行。
5. **Given** 演練正在執行, **When** 助教再次啟動部署後測試, **Then** 第二次請求被拒絕且不產生第二次演練。

---

### User Story 2 - 走的是學生真正走的那條路 (Priority: P1)

演練中的「學生」不是資料庫裡直接插入的一筆資料，而是透過與真實桌面版相同的對外 API，完成註冊／登入、取得考卷資料、提交程式碼。凡是真實學生會遇到的檢查（階段權限、加密通道、身分綁定），演練的學生也必須遇到並通過。

**Why this priority**: 若演練繞過對外 API 直接操作資料庫，它證明的是資料庫可寫，而不是考試可辦。接縫正是繞過去的那一段，也正是會壞掉的那一段。

**Independent Test**: 在演練執行期間觀察後端收到的請求，確認取卷與提交都經由對外的學生端 API 抵達，且套用了與真實學生相同的階段與身分檢查。

**Acceptance Scenarios**:

1. **Given** 演練進行到學生取卷, **When** 模擬學生索取考卷資料, **Then** 請求經由真實的學生端 API 完成，並取回可用於作答的考卷資料。
2. **Given** 考試階段尚未開放取得測資, **When** 模擬學生嘗試取得受保護的內容, **Then** 該請求被拒絕，且演練把「被正確拒絕」記為通過而非失敗。
3. **Given** 演練進行到學生提交, **When** 模擬學生送出一份程式碼, **Then** 提交經由真實的學生端 API 寫入，且之後可被助教端查得到。
4. **Given** 對外 API 在任一步回傳非預期結果, **When** 演練評估該步, **Then** 該步標記為失敗並記錄被拒絕的原因，演練停止推進。

---

### User Story 3 - 助教端手動評測確實會給出分數 (Priority: P1)

演練以助教的身分對剛剛那份模擬提交觸發手動評測，等待評測完成，並比對結果是否與預期一致。演練用的程式碼是刻意設計的：至少一份必然全對，至少一份必然答錯，因此「有分數」與「分數正確」兩件事都被驗證。

**Why this priority**: 手動評測是助教在考試中唯一的補救手段。它壞掉的時候，考試已經在進行了。而且它是整條鏈中唯一同時牽涉資料庫、評測引擎與計分邏輯的一步。

**Independent Test**: 讓演練只執行到評測段，確認必然全對的提交取得滿分、必然答錯的提交取得預期的失敗判定，且兩者的失敗歸因都不是系統錯誤。

**Acceptance Scenarios**:

1. **Given** 模擬提交已寫入, **When** 演練以助教身分觸發手動評測, **Then** 評測被接受並在有限時間內產生結果。
2. **Given** 一份必然全對的提交完成評測, **When** 比對結果, **Then** 它取得預期的通過判定與預期分數。
3. **Given** 一份必然答錯的提交完成評測, **When** 比對結果, **Then** 它取得預期的答案錯誤判定，且歸因為「學生的錯」而非系統錯誤。
4. **Given** 評測結果歸因為系統錯誤（過載、逾時、資源不足、外部服務異常）, **When** 演練評估該步, **Then** 該步一律標記為失敗，且不得被當成「成功驗證了某個學生錯誤判定」。
5. **Given** 評測在設定的等待上限內未產生結果, **When** 等待逾時, **Then** 該步標記為失敗並記錄逾時，演練繼續進行清除段。

---

### User Story 4 - 演練結束後系統回到乾淨狀態 (Priority: P1)

演練結束時——無論通過、失敗或中途中斷——系統都回到「尚未初始化」的乾淨狀態：演練考卷、演練學生、演練提交、演練分數、演練產生的裝置與紀錄全部消失，就像演練從未發生過。唯一留下的是演練報告本身。

**Why this priority**: 演練在真實系統上寫真實資料。沒有可靠的清除，這個功能就不是防線而是新的風險來源。助教必須能夠在演練之後立刻安心上傳正式考卷。

**Independent Test**: 執行一次演練，結束後檢視系統狀態與所有考試資料，確認除了演練報告之外沒有任何殘留，且系統可立即開始一場正式考試的初始化。

**Acceptance Scenarios**:

1. **Given** 演練成功結束, **When** 清除段執行完畢, **Then** 系統階段回到尚未初始化，且考卷、學生、提交、分數、裝置紀錄皆不存在。
2. **Given** 演練中途失敗, **When** 演練終止, **Then** 清除段仍然執行，系統同樣回到尚未初始化。
3. **Given** 清除段本身失敗, **When** 演練結束, **Then** 整體結論為失敗，並以明顯的警示告知助教系統仍有殘留、必須在上傳正式考卷前手動處理。
4. **Given** 演練已清除完畢, **When** 助教接著上傳正式考卷並初始化, **Then** 流程可正常進行，且正式考試中不出現任何演練資料。
5. **Given** 演練執行到一半後端重啟, **When** 系統再次啟動, **Then** 系統偵測到未完成的演練，將其標記為中斷並完成清除，不會停留在演練造成的中間階段。

---

### User Story 5 - 不會誤刪正式考卷 (Priority: P1)

助教只能在系統尚未持有正式考試資料時啟動演練。若系統已經初始化、已經上傳正式考卷或已有學生資料，啟動請求會被擋下並說明原因，不會有任何資料被清除。

**Why this priority**: 演練的清除段等同於一次全域清空。若它能在考試當天、考卷已就緒的狀態下被誤觸，它造成的損害遠大於它預防的損害。

**Independent Test**: 在已初始化並上傳考卷的系統上嘗試啟動演練，確認請求被拒絕、系統狀態與考卷完全不變。

**Acceptance Scenarios**:

1. **Given** 系統已初始化且持有正式考卷, **When** 助教嘗試啟動演練, **Then** 啟動被拒絕，並說明必須先清空系統才能演練；考卷與資料完全不變。
2. **Given** 系統尚未初始化, **When** 助教嘗試啟動演練, **Then** 啟動被允許。
3. **Given** 助教啟動演練, **When** 啟動前, **Then** 系統明確告知這次演練會在結束時清空系統，並要求助教確認。
4. **Given** 未具備管理權限的使用者, **When** 嘗試啟動演練, **Then** 請求被拒絕且不產生任何演練。

---

### User Story 6 - 演練報告可在事後查閱 (Priority: P2)

助教可以重新整理或稍後回到管理端，看到最近一次演練的完整報告：每段結果、耗時、失敗原因與時間戳記。報告在系統被清空之後依然存在。

**Why this priority**: 演練可能長於一次瀏覽器請求，且部署紀錄需要留底。報告若隨清除一起消失，助教就無法在事後說明「考前確認過了」。

**Independent Test**: 執行一次演練，重新整理頁面確認進度仍可續看；結束後重新進入頁面，確認最近一次報告完整可讀。

**Acceptance Scenarios**:

1. **Given** 演練進行中, **When** 助教重新整理管理端, **Then** 目前進度與已完成的段落重新出現。
2. **Given** 演練已結束, **When** 助教稍後回到管理端, **Then** 最近一次演練的完整報告可讀。
3. **Given** 演練的清除段已清空考試資料, **When** 查閱報告, **Then** 報告內容不受清除影響。
4. **Given** 已執行過多次演練, **When** 助教查閱, **Then** 至少可取得最近一次的報告，且報告載明執行時間。

---

### Edge Cases

- **評測引擎不可用**：演練在最早可偵測的時點失敗，明確指出是評測引擎而非考試流程的問題，並仍執行清除。
- **演練考卷本身無效**：載入段即失敗，且不進入初始化，系統狀態不變。
- **演練期間有真實裝置連上來**：演練啟動前置條件已排除正式考試資料，但若仍有裝置連線，演練必須在報告中揭露，因為清除會影響它們。
- **清除段執行時系統仍在演練的中間階段**：清除必須能從任一中間階段收斂到尚未初始化，不依賴演練走完。
- **演練耗時超過上限**：整體有硬性時間上限，逾時後強制終止並執行清除，結論為失敗。
- **模擬學生產生過長輸出**：輸出仍須受既有的截斷保護，演練不得因此凍結系統。
- **連續啟動兩次演練**：第二次被拒絕；前一次的報告不被覆寫直到新演練真正開始。
- **演練與既有的評測部署測試同時執行**：兩者共用評測引擎，系統必須拒絕其中之一而非讓兩者互相干擾。

## Requirements *(mandatory)*

### Functional Requirements

**啟動與前置條件**

- **FR-001**: 系統 MUST 在管理端提供一個明確的「部署後測試」入口，僅具管理權限者可見、可用。
- **FR-002**: 系統 MUST 僅在考試尚未初始化、且不存在正式考卷與考試資料時允許啟動演練；不符合時 MUST 拒絕並說明原因，且不得變更任何資料。
- **FR-003**: 系統 MUST 在啟動前明確告知助教本次演練會在結束時清空系統，並要求一次明確確認。
- **FR-004**: 系統 MUST 一次只允許一個演練執行中，並 MUST 拒絕與評測部署測試同時執行。

**演練內容**

- **FR-005**: 系統 MUST 自動載入一份內建的演練用考卷並完成初始化，無需助教提供任何檔案。
- **FR-006**: 系統 MUST 依既有考試階段的合法順序推進演練，不得跳階，亦不得使用任何繞過階段權限的捷徑。
- **FR-007**: 系統 MUST 以模擬學生的身分，經由真實的對外學生端 API 完成入場與取得考卷資料，並套用與真實學生相同的階段與身分檢查。
- **FR-008**: 系統 MUST 驗證「在尚未開放的階段索取受保護內容會被拒絕」，並將正確的拒絕視為通過。
- **FR-009**: 系統 MUST 以模擬學生的身分，經由真實的對外學生端 API 提交至少兩份程式碼：一份必然完全正確、一份必然答案錯誤。
- **FR-010**: 系統 MUST 以助教的身分對模擬提交觸發手動評測，等待其完成，並與預期判定及預期分數比對。
- **FR-011**: 系統 MUST 在評測結果歸因為系統錯誤時判定該段失敗，且不得將其呈現為對某個學生錯誤判定的成功驗證。
- **FR-012**: 系統 MUST 對每一段與整場演練設定時間上限，逾時 MUST 判定失敗而非無限等待。

**清除**

- **FR-013**: 系統 MUST 在演練結束時——無論成功、失敗或逾時——執行清除，使系統回到尚未初始化狀態。
- **FR-014**: 清除 MUST 移除演練產生的考卷、學生、裝置、提交、分數與行為紀錄，且 MUST 能從演練的任一中間階段收斂。
- **FR-015**: 清除失敗時，系統 MUST 將整體結論判為失敗，並以明顯警示告知助教系統仍有殘留與應採取的處置。
- **FR-016**: 系統 MUST 在啟動時偵測上一次未完成的演練，將其標記為中斷並完成清除。

**結果呈現**

- **FR-017**: 系統 MUST 在演練期間持續呈現目前段落與各段狀態，且助教 MUST 能在不離開該頁面的情況下觀看全程。
- **FR-018**: 系統 MUST 在演練結束後產生整體結論（通過／失敗）與逐段報告，含耗時、失敗原因與時間戳記。
- **FR-019**: 演練報告 MUST 在系統被清除之後仍然存在，且 MUST 可於重新整理或稍後回訪時取得最近一次的完整報告。
- **FR-020**: 報告中的任何外部輸出（程式輸出、錯誤訊息）MUST 經過長度截斷。

### Non-Functional Requirements (Constitution Mandated)

- **NFR-SEC**: 演練入口與所有演練操作 MUST 受管理權限保護；演練 MUST NOT 引入任何可繞過階段權限矩陣或身分驗證的路徑，亦 MUST NOT 提供可被外部觸發的資料清除捷徑。
- **NFR-CONC**: 演練 MUST 非同步執行，MUST NOT 阻塞管理端或其他請求，且其評測負載 MUST 受既有的全域併發上限約束。
- **NFR-TYPE**: 演練的設定、逐段結果與報告 MUST 在所有介面與資料邊界上嚴格型別化；演練考卷 MUST 綁定正式考卷的型別定義，使考卷結構演進時演練不會靜默脫鉤。

### Key Entities

- **演練（Rehearsal Run）**：一次部署後測試的執行。具備唯一識別、啟動時間、結束時間、整體結論、以及是否已完成清除。
- **演練段落（Rehearsal Stage）**：演練中的一個步驟（考卷載入、階段推進、學生取卷、學生提交、助教評測、清除）。具備順序、狀態、耗時、觀察值與失敗原因。
- **演練考卷（Rehearsal Exam Paper）**：內建的最小考卷，含足以驗證流程的題目、測資與名單。與正式考卷同結構。
- **模擬學生（Simulated Student）**：演練期間由後端扮演的學生身分，走與真實學生相同的對外 API 路徑，於清除時完全移除。
- **演練報告（Rehearsal Report）**：一次演練的完整結果，獨立於考試資料存放，不隨清除消失。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 助教在剛部署完成的系統上，能以一次確認動作啟動演練，並在 5 分鐘內取得明確的「可以辦考試／不可以辦考試」結論。
- **SC-002**: 演練涵蓋考試流程的全部四個接縫（考卷載入與初始化、學生取卷、學生提交、助教評測），每個接縫各自有獨立的通過／失敗判定。
- **SC-003**: 在刻意破壞其中任一接縫的環境下執行演練，演練 100% 判定為失敗，且指出的失敗段落與實際被破壞的段落一致。
- **SC-004**: 演練結束後，系統中殘留的演練資料筆數為 0；助教可立即開始正式考試的初始化而不需任何手動清理。
- **SC-005**: 在系統已持有正式考卷的狀態下，啟動演練的嘗試 100% 被拒絕，且正式考卷與考試資料 0 筆變更。
- **SC-006**: 演練報告在系統清除之後仍 100% 可讀，且可於演練結束後任意時間回訪取得。
- **SC-007**: 演練執行期間，管理端其他功能維持可用，且演練不造成評測引擎超出既有全域併發上限。

## Assumptions

- 演練使用**內建的演練用考卷**，助教不需準備任何檔案。理由：演練必須可重複、結果可預期，且必須能在正式考卷尚未存在時執行。以正式考卷演練會使演練的預期結果不可知，並與 FR-002 的前置條件互相矛盾。
- 演練的「清除」即為既有的**全域 reset** 語意（回到尚未初始化），不另造第二套清除工序。
- 演練以**後端對自身對外 API 發出請求**的方式扮演學生與助教，不涉及真實的桌面版應用程式；桌面版本身的驗證不在本功能範圍內。
- 演練涵蓋**流程正確性**，不涵蓋負載與併發特性——後者由既有的評測部署測試（feature 006）負責。兩者為互補而非取代。
- 演練依賴既有的評測引擎、考試階段機制與全域 reset 機制皆已可用；其中任一不可用時，演練的價值即是在考前把它指出來。
- 演練在管理端既有的部署／測試相關頁面中呈現，不新增獨立的頂層區域。
- 系統一次只服務一場考試，因此「乾淨狀態」即「尚未初始化」，不需要多租戶的隔離概念。
