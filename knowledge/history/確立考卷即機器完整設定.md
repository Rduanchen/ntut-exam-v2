# 確立「考卷即機器完整設定」

*決策日期：2026-08-26*

## 舊狀態與假設
評測相關參數原本散落在三處，且沒有一致的歸屬原則：

- 考試語意參數（`timeLimit` / `memoryLimit` / `compareMode`）在 `exam_config.judgerSettings`，隨考卷走。
- 基礎設施參數（`compile_timeout` 等）**不存在**，靜默吃 `piston-judger` 套件內硬編的預設值。
- 機器容量參數（併發上限）**不存在**，`pLimit(5)` 是寫死在 service 裡的常數。

在設計「評測器設定頁」時，提出的初始方案是**依參數的生命週期切分歸屬**。

## 被否決的選項（墓碑）

### 選項 A：基礎設施參數與考卷解耦，上傳採「有才蓋、沒有就保留」
**提案理由**：
1. `exam_config` 屬 `PROTECTED_SETTINGS_KEYS`，換考卷時整份覆寫 —— 調好的 `compile_timeout` 會被洗掉。
2. **併發上限是「這台機器的能力」而非「這份考卷的規則」**。實測顯示 12 核機器的 CE 斷崖落在併發 20–30 之間，4 核機器會低得多。考卷在機器間複製時會把錯的併發數一併帶過去，而症狀正好就是這次要修的隨機 CE。

**否決理由**：與部署模型衝突。見下方新決策。

### 選項 B：`piston-judger` 內化進 `src/`，移除 npm 依賴
**提案理由**：該套件由本專案作者自行維護，唯一使用者就是本專案；評測判定是系統的核心商業邏輯，不該綁在外部套件的發版節奏上 —— 考試前一天不會想為了改一行去發 npm 版。

**否決理由**：作者選擇維持套件的獨立性，修上游 `~/Documents/my-code/ntut-exam/node-piston` 並發布新版，本地再更新依賴。

## 觸發轉變的原因
考場部署的真實情境是**每次考試都要重新架設一台機器**（硬體不一致、經常經由筆電轉接或無線網卡連線）。在這個約束下，設定的「可重現性」壓過了「跨考卷延續性」：

> 如果設定分散在多個生命週期不同的來源，部署一台新機器就變成一份需要人工核對的清單 —— 而人工清單在考前的高壓情境下必然出錯。

## 新決策與結果
**`config.json` 即考試機器的完整設定來源。上傳採全量取代。**

1. 所有評測參數（含機器容量參數如 `maxConcurrentJobs`）都收進 `config.json`。
2. 上傳即**全量取代**，不做欄位層級的合併保留。
3. 欄位缺席 → **回落程式預設值**，而非保留現值。
4. 獨立的「評測器設定」頁仍然存在（介面切分），但**不與考卷全線切割**：頁面上改的值，下次上傳 config.json 就會被覆蓋。這是刻意的，不是缺陷。

**明確接受的代價**：跨機器複製考卷會帶著前一台機器的併發設定。緩解手段是把量測制度化 —— 部署後壓測應在考前跑出該機器的斷崖位置並據以調整（見 `draft/部署後壓測機制設計.md`）。
