# 部署後壓測機制設計 (Post-Deployment Stress Test)

## 緣起與問題
每次部署至新考場時（通常經由筆電轉接或無線網卡連線），硬體效能與網路環境皆不一致。若無部署後測試，極容易在學生考試當下才發現系統崩潰或網路瓶頸。同時，我們需要符合行業標準的精確數據（如 P99 延遲、RPS、錯誤率）來評估主機負載能力。

**2026-08-26 的 Piston 隨機 CE 事件驗證了這個提案的必要性**：問題正是在真實考試中才被發現，且症狀（學生被誤判 CE）直接傷害考試公平性。若部署當下就跑過一次併發 sweep，斷崖位置會在考前而非考中暴露。詳見 `draft/piston穩定度與併發問題.md`。

## 設計提案
引入「部署後壓測機制」，結合後端效能測試與前端 Admin UI，讓管理員能一鍵執行並檢視報告。

### 具體機制
1. **後端整合 `autocannon`**：
   - 在後端實作專屬壓測 API（如 `POST /api/admin/system-test`）。
   - API 內部透過 Node.js 呼叫 `autocannon` 模組，對系統自身的評測端點發起模擬高併發請求（可配置併發數與持續時間）。
   - 收集並回傳標準效能數據（Percentiles、RPS、Timeout 統計等）。
2. **前端 Test Tab 實作**：
   - 在 Admin UI 新增 `Test Tab`（測試頁籤）。
   - 提供「啟動壓測」介面，讓管理員設定參數。
   - 接收後端回傳的 JSON 報告後，利用圖表視覺化呈現延遲分布與穩定度。

### 追加：併發 sweep — 找「斷崖」而非「平均值」
Piston 事件證明**平均延遲與 RPS 不足以描述評測系統的風險**。真正要找的是**臨界點**：負載不是漸進劣化，而是撞到某個硬逾時後突然崩塌。

手法（2026-08-26 實證有效）：
1. 固定一份代表性程式碼（用重編譯成本高的，如 `#include <bits/stdc++.h>`）。
2. 沿**併發軸**掃描（1 → 5 → 8 → 12 → 16 → 20 → 30…），每檔送固定數量請求。
3. 記錄每檔的 **max 延遲**與**非 AC 率**，找出兩者暴增的交界。
4. 建議營運併發設在斷崖的一半以下。

該次量測（12 核 Mac、閒置）：併發 20 時 max 7.3s / CE 0%，併發 30 時 max 10.6s / **CE 23%** — 斷崖落在 20–30 之間。

**這也是壓測必須回報 max 而非只回報 p50/p99 的理由**：斷崖是被單一硬上限（`compile_timeout`）切出來的，平均值在崩塌前一刻看起來仍然健康。

### 追加：壓測必須跑在「本機的真實負載」下
上述數據是在閒置機器、只跑 Piston 的條件下取得的。實際考試機同時跑 backend、frontend、SQLite 與作業系統，餘裕會顯著更小。壓測 API 的價值正在於它跑在**那台機器的真實狀態**下 — 因此它不能只是開發期的一次性測量，而必須是**部署後的例行關卡**。
