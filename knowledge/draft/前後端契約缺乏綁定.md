# 前後端契約缺乏綁定

## 觀察
`frontend/src/types/config.ts` 的 `judgerSettings` 在 feature 004 之後有一段時間仍描述著
**004 之前的 schema**（三個欄位，而後端已有七個）。沒有任何東西發現這件事，因為
**沒有任何東西把前端型別綁到後端 schema**。

發現時機是 005 的勘查——而 005 的整個頁面內容就是那份契約。若不是這個 feature 剛好要讀
那些欄位，漂移會繼續存在下去。

## 為什麼這值得記
`experience.md` #4 記過同一個形狀：「沒有 oracle 的東西會腐化」。當時的結論是
**fixture 必須型別綁定到 production schema 且只有單一來源**。

前端與後端之間目前**完全沒有這個綁定**。後端的 zod schema 是唯一真相，前端手抄一份 TS
interface，兩者靠人的記憶保持同步。這不是「可能會漂移」，是**已經漂移過一次**。

## 005 做了什麼、沒做什麼
- ✅ 補上了缺的欄位。
- ✅ 新增獨立的 `typecheck` script——先前 `vue-tsc` 只在 `build` 時跑，等於型別檢查
  不在日常路徑上。**不會被routinely執行的檢查不是守衛。**
- ❌ **沒有**建立兩者之間的綁定。那需要跨前後端的機制，超出 005 的範圍。

所以下一次漂移仍然會發生，只是現在**跑一次 typecheck 就看得見**——前提是有人跑。

## 可能方向
1. 後端以 zod schema 產生 TS 型別，前端直接消費產物。
2. 共用 package 放置契約型別，前後端都 import。
3. 契約測試：前端對著後端真實回應驗證自己的型別假設。

方向 1 最接近「單一真相來源」，也最符合 experience #4 的教訓。

## 另外兩個同源的發現（來自 005）
- **Piston 容器設定無法被回報**。它們是 container 環境變數、只在啟動時讀取，所以
  設定頁只能標示「不可回報」而非顯示值。要顯示就需要後端新增端點。
- **語言映射只存在於後端**（`Cpp → c++`）。005 用 Piston 回報的 aliases 繞過了複製映射表
  的需求，但那是**推論**；後端明確提供映射會更穩固。

## 狀態
In-flight Rationale。三個發現都需要後端變更，都被 005 明確排除，記錄於此避免遺失。
