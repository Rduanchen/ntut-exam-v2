# 全專案環境標準化

## 緣起與問題
目前專案（包含 Host 端、前端、後端）的 `package.json` 中缺乏統一的 Node.js 版本規範（未設定 `engines` 或 `.nvmrc`），這可能導致不同開發者或 CI/CD 環境下運行結果不一致。

## 解決方案提案
1. 在根目錄及各子專案的 `package.json` 加入 `engines` 限制（例如鎖定 Node.js >= 20）。
2. 增加 `.nvmrc` 以利開發者快速切換環境。
3. 在部署腳本 (`deploy.sh`, `Dockerfile`) 中落實單一伺服器及 LTS 版本的策略配置。

## 升格：這已經不是整潔性問題，是正確性需求

2026-08-27，feature `004-judge-backend-migration` 讓 Node 的最低版本變成**承重的**：
後端以 CommonJS 編譯，而 `p-limit@7` 是 ESM-only，從 CommonJS `require()` 一個 ESM 套件
的能力在 **Node 20.19** 才出現。實測 20.20.2 可以、20.18.0 拋 `ERR_REQUIRE_ESM`。

失敗發生在啟動當下，訊息與成因看起來毫無關聯。而 `Dockerfile` 當時釘的是 **`node:20-alpine`
這個浮動標籤**——建置時解析成當下最新的 20.x，今天剛好滿足，但沒有任何地方記錄它必須滿足。
哪天在較舊的 20.x 上重建就會炸。

已在 004 中處理：`backend/package.json` 宣告 `engines: { node: ">=20.19.0" }`，
`Dockerfile` 改釘 `node:22.23.2-alpine`。

**推論**：這份 draft 原本的理由是「不同環境下運行結果可能不一致」——那是機率性的隱憂。
現在有了具體的、可重現的失敗案例。**其餘子專案（前端、根目錄）仍未宣告 `engines`，
且仍無 `.nvmrc`。** 一個真實案例足以說明：版本約束若不寫下來，就只存在於某個人的記憶裡。
