# 失敗歸因的隔離 (Fault Attribution Isolation)

## 定義
在一個「系統代替使用者執行某件事、再對結果下判定」的架構裡，**判定結果必須能回答「這是誰的失敗」**。
使用者的失敗（程式寫錯）與系統的失敗（過載、逾時、資源不足、外部服務異常）必須落在不同的分類上，且分類器不得讓後者偽裝成前者。

## 為什麼是概念而非單一教訓
它同時投影在三個維度上：

- **規範面 (Principles)**：衍生原則「失敗歸因的隔離」——系統性失敗一律不得判為學生錯誤；歸屬不明時偏向判系統錯誤並重試。
- **情境面 (Vision)**：架構上需要一個獨立於使用者結果的 SE（System Error）分類、自動重試路徑，以及讓 TA 看得見「有多少判定其實是系統造成的」的監控。
- **存在面 (Experience)**：2026-08-26 的 Piston 隨機 CE 事件是實際踩到的代價。

## 修剪力 (Pruning Power)
對任何一個判定結果問：

> **有沒有某種系統狀態，能單獨產生這個判定？**

若有，分類器就是錯的 —— 不論它平常看起來多正確。

這把尺會逼出一個容易被忽略的推論：**「非零 = 失敗」是不夠的**。
必須進一步區分「非零因為使用者」與「非零因為我們殺了它」。被信號終止（`code: null` + `signal: SIGKILL`）在數值上與「編譯器回報語法錯誤」無法區分，但語意上是相反的兩件事。

## 已識別的同形案例
用上述尺度回掃知識庫，至少三處是同一個形狀：

1. **`compile.code !== 0` → CE**（2026-08-26）
   編譯階段被 wall-clock 逾時 SIGKILL 時 Piston 回 `code: null`，`null !== 0` 成立 → 判學生 CE，且 `stderr` 為空，訊息是 `Compilation Error: Unknown error`。**系統過載被記在學生帳上。**

2. **`isMemoryExceeded` 用 `stderr.includes("Killed")`**
   把**使用者輸出**當成**系統訊號**讀。學生程式自己印出 "Killed" 就被判 MLE。這是歸因隔離的鏡像失敗：不是系統偽裝成使用者，而是使用者能偽造系統訊號 —— 因此它同時也是一個防作弊面向的漏洞。

3. **`experience.md` #1 輸出過長導致系統凍結**
   系統承受不住使用者輸入而崩潰，當時缺乏歸屬機制，症狀表現為 SE。修法（輸出截斷）處理了成因，但沒有建立「這是系統的極限，不是學生的錯」這層語意。

## 設計上的要求
1. **執行層與判定層分離**：執行層只回報事實（各 stage 的 `code` / `signal` / `status` / `message` 原始值），判定層才做語意映射。執行層不得預先把資訊壓成單一 status —— **壓縮即資訊遺失，且不可逆**。
2. **系統性失敗要能自動重試**，因為它與提交內容無關，重試是有意義的（使用者錯誤重試則毫無意義）。
3. **系統性失敗要被計數並可觀測**。若一場考試中 SE 比例異常，那是機器的警報，不是學生的成績。
4. **使用者可控的資料（stdout/stderr）永遠不得作為系統狀態的判斷依據。**

## 一個反覆出現的訊號
> **當呼叫端被迫繞過某個抽象時，那個抽象就是壞的。**

`judger.service.ts` 在呼叫 `judge()` **之前**已經手動前置判斷 `executeRes.success === false || executeRes.error || !executeRes.run`。
那段防禦性程式碼是 bug 的自白 —— 它證明了作者當時已隱約知道 `judge()` 的分類不可信，只是繞過去而沒有回頭修分類器。**繞過抽象的程式碼值得被當成 code smell 主動搜尋。**
